# DocMirror 技术架构说明

客户阅读版 | 把商业凭证转成可用、可核查的数据

编制日期：2026年8月27日

> DocMirror 是连接“原始文件”和“业务系统”的文档处理服务。它读取文件中的文字与表格，整理出日期、金额、账户等业务信息，并提供来源线索和质量提示，让人员与系统知道结果从哪里来、哪些地方需要复核。

## 它在业务中做什么

可以把 DocMirror 理解为一位“会整理材料、会标注出处的资料员”。它帮助完成录入和核对的前半段工作，后续审批、分析或业务决策仍由客户的系统与人员负责。

- 减少重复录入：把分散在文件中的信息整理成统一字段和明细表。
- 方便核对原文：为可定位的信息保留页码、原文位置或来源引用。
- 连接现有系统：让财务、审核、数据分析和知识库等应用接收同一批处理结果。

## 当前重点处理的材料

| 材料类型 | 典型整理内容 |
| --- | --- |
| 银行流水 | 账户信息、交易日期、收支金额、余额、交易对手 |
| 微信支付记录 | 支付与收款明细、交易时间、金额等 |
| 支付宝记录 | 交易明细、收支信息、交易对手等 |
| 增值税发票 | 发票信息、购销双方、金额与税额等 |
| 营业执照 | 企业名称、统一社会信用代码等登记信息 |
| 征信报告 | 个人或企业报告中的账户、授信、还款、查询等信息 |

常见输入包括 PDF、扫描件、图片，以及 Word、Excel、PowerPoint 文件；具体格式取决于已安装的解析组件，部分旧格式需要转换工具。

其他材料可进入通用解析流程，提取文本、表格和可识别字段。**“能够读取文件”不等于“已具备该行业全部业务规则”**；具体字段与版式适配情况需要用客户样本确认。

### 为什么要有一份“共同底稿”

文字、表格、页面位置和质量信息先进入同一条处理流程，完成后形成固定快照。业务整理模块和审计输出各自读取这份底稿，不回写修改底稿，减少不同出口各自重新解析带来的口径差异。底稿被固定不代表识别内容一定正确，质量问题仍需复核。

### 专业规则与通用能力如何配合

核心负责读懂文件的基础结构；领域插件负责把这些信息整理成银行流水、发票、征信等业务记录。新增场景可以扩展对应规则；如果基础信息没有被正确读取，仍需改进核心解析或补充原始材料。

### AI 在哪里发挥作用

扫描件可使用本地 OCR，即“识别图片中的文字”。外部 OCR 和大模型属于可选增强，并非基础运行的必需条件；启用前需确认服务、费用和允许发送的数据，增强后的结果同样需要质量检查。

## 客户能拿到什么

DocMirror 为系统、人员和核查工作提供不同形式的结果。常规交付以结构化结果、可读正文和数据表为主，详细解析与审计材料按实际交付配置提供。

| 结果形式 | 通俗解释 | 主要用途 |
| --- | --- | --- |
| 结构化结果（JSON） | 按统一字段组织的业务信息与明细记录 | 系统对接、后续计算 |
| 可读正文（Markdown） | 按阅读顺序整理的正文与原始表格内容 | 人员阅读、知识库输入 |
| 数据表（CSV） | 按业务记录整理的表格文件 | Excel 查看、筛选、统计 |
| 字段审计表及详细材料 | 原始值、来源线索、质量或诊断信息，依产物范围提供 | 复核、排错、追溯 |

不同输出用途不同：可读正文侧重原文阅读，业务数据表侧重可计算的记录。部分业务 JSON 会精简技术细节，完整字段证据应从对应审计材料获取，不能假定每个输出文件都包含全部证据。

### 用一条流水说明

以下为虚构示例，仅用于解释处理方式，并非实际运行结果。

> 原文：交易日期 2026/08/01，收入人民币 5,000.00 元，付款方为甲公司。整理后：日期为 2026-08-01，收入为 5000.00，币种为人民币，付款方为甲公司；可定位时，附上第 2 页对应交易行的来源信息。如果数字模糊或同一字段存在冲突，应提示人工核对，而不是把猜测当作已确认事实。

### 如何决定是否直接使用

建议在客户业务流程中设置三种处理方式：

- 信息清楚且检查通过：按双方约定的业务规则继续处理。
- 信息模糊、相互矛盾或来源不足：进入人工复核，查看原文后确认。
- 文件失败或内容明显缺失：补充清晰文件、修正配置或重新处理。

**质量分是复核线索，不是准确率承诺。**“任务完成”不代表每个字段都正确；可追溯也不等于对凭证真实性作出鉴定。最终是否入库、审批或用于分析，应由客户的业务规则决定。

## 部署在哪里，数据由谁控制

DocMirror 可在本地服务器或客户指定的私有环境中运行。客户可以通过已有系统调用它，也可以由技术人员执行批量处理；不要求把材料上传到一个公共网站。

### 客户内网或私有环境

在本地解析与本地 OCR 方案下，文件可在客户控制的环境中处理。若要求完全离线，需要预先备齐模型和依赖、关闭外部 OCR 与大模型，并在网络层限制外连，最后通过断网测试确认。

### 获准使用外部识别服务

对需要增强识别的场景，可以在明确授权后评估外部 OCR 或大模型。应事先确认哪些文字或页面会被发送、发给谁、如何留存以及产生哪些费用；这属于额外配置，不应视为本地部署的默认行为。

### 上线时需要落实的安全措施

- 访问控制：正式服务应配置接口密钥并启用 HTTPS。当前接口密钥为可配置项，不能按未配置密钥的开发方式直接开放服务。
- 数据留存：明确原始文件、处理结果和运行记录的保留范围、存储位置、访问权限、备份与清理周期。
- 对外分享：日志和支持材料可应用脱敏规则；业务交付文件可能保留完整姓名、账户等内容，需另外控制导出与共享权限。
- 网络边界：结合本地隐私策略、外部服务配置和服务器网络规则验证数据流向，不能仅凭“私有部署”认定不会外发。

### 服务如何运行与扩展

当前基础形态是可本地部署的处理服务，支持单文件、多文件任务、进度查询和结果文件存储。可采用 Docker 容器统一运行环境。更高并发、多节点容灾、单点登录、细分权限和存储加密等要求，需要结合客户环境另行设计与验证。

技术选型简述：Python 处理核心、FastAPI 服务接口、按格式选择的文档解析组件，以及可选的本地 OCR。实际容量与处理速度受页数、文件质量、硬件和配置影响，应以客户样本实测为准。

## 怎样接入现有业务

DocMirror 可以作为现有系统中的文档处理服务。面向业务人员的上传页面、审批流程和人工复核工作台，由客户现有系统承接或作为项目范围另行建设。

1. 提交材料：现有系统通过接口上传单个或多个文件，取得任务编号。
2. 查询进度：查看处理中、完成、部分失败或失败等状态；也可按接口配置同步等待。
3. 获取结果：下载所需结果文件，依据质量提示和客户规则完成复核，再进入后续业务。

API 是“软件之间的接入口”；SDK 是“帮助开发人员接入的工具包”。业务人员通常不需要直接操作这些技术工具。

### 交付范围如何确定

| 能力范围 | 交付说明 |
| --- | --- |
| 基础解析与标准结果 | 包括核心解析、现有领域规则、来源与质量信息、接口及常规输出；所需可选组件需安装齐全 |
| Enterprise / Finance 商业扩展 | 独立分发并受授权约束；不能把产品定位直接当作已交付功能，具体以扩展包与确认清单为准 |
| 客户专属能力 | 新版式适配、专属规则、业务工作台及系统对接等，需确认范围后实施与验收 |

### 上线前共同确认四件事

- 材料范围：提供经过授权的代表性样本，覆盖常见版式、清晰度和异常情况，确认要支持哪些文件。
- 字段范围：明确必需字段、记录粒度、日期与金额口径，以及无法确定时如何处理。
- 安全范围：确定部署位置、是否允许外部服务、数据保留周期、访问与共享权限。
- 验收范围：实测关键字段正确率、记录完整性、来源可定位情况和处理时长，并约定人工复核与失败处理方式。

> 交付目标：让文档中的信息更容易进入业务，同时保留核查依据。对于模糊材料、新版式和高风险字段，保留人工确认环节，是稳妥使用系统的一部分。
